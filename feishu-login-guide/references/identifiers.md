# 飞书用户标识符：哪个能用来做长期授权

> 一句话：**`open_id` 用来认「这次会话是谁」，`user_id` / `union_id` 用来记「这个人长期是谁」。**
> 拿 `open_id` 存权限白名单，会在换飞书应用的那天静默锁死所有人。

## 三个标识符的作用域

| 标识符 | 作用域 | 换应用后 | 拿到它的条件 | 适合做什么 |
|---|---|---|---|---|
| `open_id` | **单个应用内**唯一 | **会变** | user_info 接口直接返回，无需额外权限 | 当次会话身份、调用同一应用的其他飞书 API |
| `union_id` | 同一开发者（服务商）名下多应用间一致 | 同开发者内不变 | 同上，通常一并返回 | 同一团队多个应用之间关联同一个人 |
| `user_id` | **租户（企业）内**唯一 | **不变** | 需要通讯录权限（如 `contact:user.employee_id:readonly`），未授权时为空 | 权限白名单、管理员名单、长期数据归属、审计记录 |
| `employee_id` / 工号 | 企业自己维护 | 不变 | 需通讯录权限且企业有填 | 和 HR 系统对账 |

关键点：**`open_id` 的「唯一」是「在这个应用内唯一」，不是「这个人唯一」。** 同一个人：

- 在 App A 下是 `ou_4282…564c`
- 在 App B 下是 `ou_f794…faa0`

两个值毫无关联，无法互相推导。

## 什么时候会踩到

只要发生下面任一件事，所有存下来的 `open_id` 就一起失效：

- 新建了一个飞书应用来替换旧的（改名、换主体、重建）
- 从「自建应用」迁到「商店应用」或反之
- 从双 App（FBIF + 富的）合并成单 App，或反过来拆分
- 换了开发者账号重新创建应用

失效的样子**特别隐蔽**：

- 配置文件里白名单还在，值看起来完全正常（`ou_` 开头，长度对）
- 服务启动无报错，健康检查正常
- 用户能登录成功，只是登录后所有受限功能都提示「没有权限」
- 日志里通常什么都没有——因为「白名单没命中」在代码里往往只是一个 `return false`

## 正确写法

授权判定按 `user_id` → `union_id` → `open_id` 顺序匹配，三种都接受。这样既优先用稳定标识，又不破坏已有的 `open_id` 配置：

```go
// matchesACL 按 user_id → union_id → open_id 顺序匹配白名单。
//
// open_id 是「每个飞书应用一套」的：同一个人在不同应用下 open_id 不同，换应用或
// 新建应用后旧值会静默失效——白名单还在，人却进不来，且没有任何报错指向根因。
func matchesACL(set map[string]struct{}, user SessionUser) bool {
	for _, id := range []string{user.UserID, user.UnionID, user.OpenID} {
		if id == "" {
			continue // 空串不得匹配白名单里可能存在的空条目
		}
		if _, ok := set[id]; ok {
			return true
		}
	}
	return false
}
```

配套三件事，缺一个下次还会卡住：

1. **登录成功时把三个 ID 都记进日志**（`open_id` / `user_id` / `union_id` / 姓名）。授权名单要填什么值，只能从这里取——`open_id` 不出现在任何界面上，管理员没有别的途径知道该填什么。
2. **权限被拒时也记一条日志**，带上同样三个 ID 和「该把它加到哪个环境变量」的提示。否则运维只能靠猜。
3. **写测试固定住**：至少覆盖「user_id 命中」「union_id 命中」「open_id 命中（兼容旧配置）」「只配了旧应用的 open_id 必须落空」「空标识不得匹配空串」五种情况。

## 环境变量命名

已有项目里如果变量已经叫 `*_OPEN_IDS`，**不要为了正名去改名**——改名要同步改所有部署环境的配置文件，收益不抵风险。做法是：保留变量名，在 README 和变量注释里写明「接受 user_id / union_id / open_id，优先填 user_id」。

新项目直接命名为 `*_USER_IDS` 或 `*_ALLOWED_IDS`，避免把实现细节焊死在变量名里。

## 排查清单

用户报「登录成功但没权限」时按顺序查：

1. 白名单环境变量**是否存在**（不是「值对不对」，先确认变量本身配了没）——新加的权限检查上线时最容易漏配
2. 服务进程**实际加载**的值：`tr '\0' '\n' < /proc/<pid>/environ | grep <VAR>`，而不是只看配置文件（改了文件没重启就是这个症状）
3. 日志里**当次登录的真实 ID**，和白名单里的值逐字符比对
4. 如果两个 `open_id` 都以 `ou_` 开头但完全不同 —— 就是本文说的换应用问题，改用 `user_id`
5. `user_id` 为空 → 应用缺通讯录权限，去飞书后台加 `contact:user.employee_id:readonly` 后**重新授权**（老 session 里不会补上）

## 事故记录

**2026-08-05，FoodTalks Antispam（antispam.fbif.com）**

一次部署里包含了新增的 `review.read` 白名单权限检查，但部署时没配对应的环境变量，导致所有人登录后都看到「当前账号没有审核查看权限」。

修复过程中第二次踩坑：从历史审核记录（`state.json` 的 `operatorId`）里取出了该用户的 `open_id` 填进白名单，**仍然进不去**——因为历史记录是旧飞书应用时期写的，`open_id` 早就变了。最后靠临时加登录日志，拿到当次登录的真实 `open_id` 才修好。

两个教训：

- 部署带新权限检查的代码，必须同时确认目标环境的授权名单**已配置且非空**；代码能编译、测试能过、服务能起，都证明不了这一点。
- 任何从历史数据里捞出来的 `open_id`，都要先怀疑它是不是旧应用时期的。
